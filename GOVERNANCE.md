# Governance

## IN2NEXT Nexus

This document defines the governance model, project roles, decision-making processes, contribution pathways, technical responsibilities, and long-term stewardship of the IN2NEXT Nexus project.

Nexus is an open-source project stewarded by IN2NEXT Solutions and developed with contributions from developers, designers, researchers, engineers, data scientists, AI/ML specialists, robotics engineers, technical writers, and the wider open-source community.

The purpose of this document is to provide a clear, transparent, and sustainable framework for building and maintaining Nexus as the project grows.

---

## 1. Purpose

The governance model exists to ensure that Nexus remains:

- Open to community participation
- Technically coherent
- Secure and maintainable
- Transparent in major decisions
- Welcoming to contributors
- Accessible to contributors of different experience levels
- Sustainable over the long term
- Responsible toward users and the wider ecosystem

Governance should enable contribution rather than create unnecessary bureaucracy.

As Nexus grows, governance may become more formal where project scale requires it.

## 3. Governance Principles

Nexus governance follows the following principles.

### 3.1 Transparency

Important project decisions should be understandable and documented.

Where practical, discussions about project direction, architecture, features, and technical decisions should occur in public project spaces.

Security-sensitive matters, private contributor matters, and other confidential matters may be handled privately.

### 3.2 Open Contribution

Contributors should have a clear path to participate regardless of their experience level or technical discipline.

A contributor does not need to be a senior engineer to make a valuable contribution.

### 3.3 Merit Through Sustained Contribution

Project responsibilities should generally be earned through consistent, constructive, and high-quality participation.

Technical ability is important, but maintainership also requires:

- Reliability
- Communication
- Judgment
- Security awareness
- Documentation
- Collaboration
- Community responsibility

### 3.4 Technical Quality

Changes should be evaluated according to:

- Correctness
- Security
- Maintainability
- Performance
- Scalability
- Accessibility
- Usability
- Testing
- Documentation
- Long-term project impact

### 3.5 Security

Security is a project-wide responsibility.

Security-sensitive decisions may require additional review and may be handled through private channels where public discussion would create unnecessary risk.

See [SECURITY.md](SECURITY.md).

### 3.6 Documentation

Important decisions, public interfaces, architectural changes, development processes, and contributor processes should be documented.

### 3.7 Respectful Disagreement

Technical disagreement is expected and can improve the project.

Disagreements should focus on:

- Evidence
- Requirements
- Trade-offs
- Technical reasoning
- User impact

Disagreement should never become personal harassment or hostility.

### 3.8 Long-Term Sustainability

Short-term convenience should not automatically outweigh:

- Maintainability
- Security
- Contributor experience
- Project stability
- Operational requirements
- Long-term project health

# 4. Community Roles

Nexus uses a progressive contribution model.

```text
Community Member
       |
       v
Contributor
       |
       v
Active Contributor

       v
Reviewer
       |
       v
Maintainer
       |
       v

```
These roles describe project responsibilities and trust levels.

They do not necessarily correspond directly to GitHub organization roles.

4.1 Community Member

A Community Member is anyone participating in the Nexus ecosystem.

Examples include people who:

Ask questions
Participate in Discussions
Report issues
Test releases
Provide feedback
Participate in community activities
Follow project development

Community members do not automatically receive repository write access.

4.2 Contributor

A Contributor is a person who has made an accepted contribution to the project.

Contributions may include:

Documentation
Design
Testing
Bug reports
Research
Accessibility improvements
Examples
Community support
Translations
Developer tooling

Contributors generally participate through:

Issues
Discussions
Forks

Pull requests
4.3 Active Contributor

An Active Contributor is someone who consistently participates in the project.

Examples include contributors who:

Regularly submit quality pull requests
Review changes
Improve documentation
Help other contributors
Participate constructively in technical discussions
Maintain an area of the project
Help reproduce and resolve issues

Active contribution may be considered when assigning additional project responsibilities.

A reviewer may evaluate:

Correctness
Testing
Security
Documentation
Architecture
User experience
Performance

Review authority should generally be limited to areas where the reviewer has sufficient knowledge.

4.5 Maintainer

Maintainers are trusted contributors with responsibility for one or more areas of Nexus.

Maintainer responsibilities may include:

Reviewing pull requests
Merging approved changes
Triaging issues
Maintaining documentation
Supporting contributors
Participating in technical decisions
Maintaining project quality
Coordinating releases
Identifying technical debt
Supporting project security
Maintaining assigned project areas

Maintainers are expected to act in the long-term interests of the project rather than for personal preferences.

4.6 Core Maintainer

Core Maintainers have broader responsibility across Nexus.

Responsibilities may include:

Cross-area architecture
Major technical decisions
Release coordination
Governance

Maintainer coordination

Long-term technical direction

Core Maintainer status represents significant project trust and responsibility.

5. GitHub Organization Roles

Project governance roles and GitHub administrative roles are separate concepts.

GitHub organization permissions should follow the principle of least privilege.

Not every contributor or maintainer needs organization Owner privileges.

Possible GitHub access levels may include:

Organization Owner
Organization Member
Repository Administrator
Repository Maintainer
Repository Contributor
Outside Collaborator

Access should be granted according to the responsibilities of the individual.

5.1 Organization Owners

Organization Owners are responsible for administrative control of the GitHub organization.

Owner access should be restricted to highly trusted individuals who require it for organizational administration.

Technical contribution alone does not automatically justify Owner access.

Organization Owners may be responsible for:

Organization security
Billing
Organization settings
Repository administration
Team management
Access control
Security policies
Administrative infrastructure
6. Maintainer Responsibilities

Maintainers are expected to:

Review contributions fairly.
Communicate clearly.

Protect project security.
Keep documentation current.
Help new contributors understand the project.

Maintainer status is based on sustained contribution and project trust.

8. Maintainer Removal or Role Changes

Maintainer responsibilities may be changed, reduced, suspended, or revoked when necessary.

Reasons may include:

Prolonged inactivity
Repeated failure to perform assigned responsibilities
Serious security violations
Abuse of project privileges
Repeated violations of the Code of Conduct
Serious misconduct
Conflict of interest that cannot be appropriately managed
Actions that materially harm project security or integrity

Where practical, maintainers should be given an opportunity to discuss concerns before a role is changed.

Immediate action may be appropriate in serious security or community-safety situations.

10. RFC Process

RFC stands for Request for Comments.

An RFC is a structured proposal for a significant technical or product decision.

A typical RFC process is:

Problem
   |
   v
Proposal
   |
   v
Discussion
   |
   v
Technical Review
   |
   v
Decision
   |
   v
Implementation
   |
   v
Documentation
10.1 When to Create an RFC

An RFC should be considered when a proposed change:

Has significant architectural impact.
Introduces a new major subsystem.
Changes public APIs.
Changes security boundaries.
Introduces a new extension mechanism.
Changes the data model substantially.
Introduces major AI capabilities.
Changes workflow execution behavior.
Introduces physical-device or robotics control.
Creates significant backwards-compatibility concerns.
Introduces significant infrastructure requirements.

Not every feature requires an RFC.

11. RFC Contents

A useful RFC should normally include:

## Summary

## Problem

## Non-Goals

## Alternatives Considered

## Security Considerations

## Compatibility

## Migration Plan

## Testing Strategy

## Operational Considerations

## Open Questions

## Decision

RFCs should explain trade-offs rather than simply advocating for one implementation.

12. Technical Decision Criteria

When evaluating a significant technical decision, maintainers should consider:

User Value

Does the change solve a meaningful problem?

Security

Does the design introduce new attack surfaces, data risks, or permission risks?

Maintainability

Can future contributors understand and maintain it?

Complexity

Does the benefit justify the additional complexity?

Performance

Does the design meet expected performance requirements?

Scalability

Can the architecture evolve as Nexus grows?

Compatibility

Will existing users, APIs, plugins, integrations, or deployments be affected?

Developer Experience

Does the change make contribution easier or harder?

Operational Requirements

Does the change introduce infrastructure, hosting, monitoring, or operational costs?

Community Impact

Does the change affect contributors, plugin authors, integrators, or users?

17. AI Governance

AI is expected to become an important part of Nexus.

AI features should follow the following principles.

Human Accountability

People remain responsible for consequential system actions.

Least Privilege

AI agents should receive only the permissions required for their intended tasks.

Explicit Tool Boundaries

Agents should have clearly defined tools and capabilities.

Validation

Important AI-generated outputs should be validated before consequential use.

Auditability

Where appropriate, AI actions should be logged in a way that supports debugging, monitoring, and accountability.

Human Approval

High-impact actions should require explicit human approval where appropriate.

Examples may include:

Production deployment
Destructive operations
Sensitive data access
External communication
Financial actions
Permission changes
Physical-device control

21. Versioning

Once Nexus reaches a stable release process, the project intends to use Semantic Versioning where practical.

MAJOR.MINOR.PATCH

Example:

1.4.2
MAJOR

Used for incompatible changes.

MINOR

Used for backwards-compatible functionality.

PATCH

Used for backwards-compatible bug fixes and maintenance changes.

Before 1.0.0, APIs and architecture may change more frequently.

Release-specific compatibility expectations should be documented in the relevant release notes.

25. Conflict of Interest

Contributors and maintainers should disclose relevant conflicts of interest when they could materially affect a project decision.

Examples may include:

A proposed dependency is controlled by the decision-maker.
A contributor has a direct commercial interest in a proposed integration.
A decision materially benefits a maintainer's separate business.
A contributor is evaluating a competing commercial product.
A contributor has a financial relationship with a vendor under consideration.

A conflict does not automatically disqualify someone from participating.

Appropriate disclosure and, where necessary, recusal should be used to preserve trust.

27. Intellectual Property

Contributors must follow the project's applicable contribution and licensing requirements.

The project may establish a formal Contributor License Agreement (CLA) or Developer Certificate of Origin (DCO) process as Nexus grows.

Until a formal contribution-rights mechanism is adopted, contributors should not submit code or other material that they do not have the right to contribute under the project's applicable license and contribution terms.

Third-party code, assets, datasets, documentation, models, and dependencies must comply with their applicable licenses and terms.

28. Trademarks

Open-source licensing of Nexus source code does not automatically grant permission to use IN2NEXT Solutions or Nexus trademarks, logos, names, or branding in ways that imply endorsement, sponsorship, or affiliation.

Trademark policies may be documented separately as the project and brand mature.

38. Governance and Open Source Licensing

Nexus governance operates alongside the project's open-source license.

The project license defines the permissions granted to users and contributors regarding the licensed source code.

Governance defines how the project itself is developed, maintained, reviewed, and managed.

These are separate concepts.

The applicable license is defined in LICENSE.
